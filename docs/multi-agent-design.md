## 1. 目标与现有基线

### 已确认的首个验收场景

一个具体代码任务，由多个 Agent 分工实现、审查，并在发现冲突后完成纠正。验收重点是消息是否实际改变了行动，以及任务最终是否完成，不能仅凭消息成功收发判定协作有效。

### 当前代码事实

- TypeScript、Node.js 24+、ESM；锁定及安装的 `@anthropic-ai/claude-agent-sdk` 版本为 `0.3.267`。
- `src/agent.ts` 当前使用字符串 prompt 启动单次 query，在收到首个 result 后结束，并关闭 SDK 子进程。
- `src/config.ts` 当前只开放 `Read`、`Glob`、`Grep`，未接入应用的多 Agent 编排、inbox、讨论室或恢复机制。
- 当前代码尚不能完成目标中的代码修改任务。后续需要单独设计主世界执行 Agent 的写入权限；讨论 fork 的只读要求不代表所有主世界 Agent 永远只读。
- 本文是设计基线，不是已交付能力清单。

## 2. 设计来源与边界

来源：[Raft — Is Having Agents in the Room Meant to Be Chaotic?](https://raft.build/resources/blog/is-having-agents-in-the-room-meant-to-be-chaotic/)。

文章中与本项目相关的两个机制：

1. **Agent inbox**：把通知变成可查询的项目，Agent 决定读取什么，避免把所有聊天直接塞入工作上下文。
2. **Held draft**：发送时检查草稿所依据的房间版本。状态变化时保留草稿，并允许修改、重新检查后原样发送、保持沉默或显式强制发送。

文章不自动解决任务归属、文件并发写入、执行幂等或外部副作用。讨论 fork、多数投票和 super agent 是本项目提出的机制，不应归为文章已经验证的方案。Held draft 是否纳入第一版仍待决定。

## 3. 已确认的产品要求

| 编号 | 要求 | 边界 |
| --- | --- | --- |
| D01 | 以具体代码任务验证分工、实现、审查和冲突纠正 | 不以“能互相聊天”代替任务验收 |
| D02 | inbox 维护多 Agent 消息，并提供 `view_inbox` | 已读确认按 D47，三档展示按 D48，运行中提醒按 D49、D50，自然空闲唤醒按 D51；具体接口及异常恢复仍待决定 |
| D03 | 普通 @ 在可控执行边界处理；用户显式停止使用独立中断通道 | 中断不能撤销已经发生的文件写入或外部操作 |
| D04 | 应用重启后保留消息、读取进度与会话关联，检查任务状态后恢复 | 操作重试的去重与结果核验另行设计，不默认重放执行 |
| D05 | A @ B 后，若 B 认为命令与自身判断冲突，B 可通过工具发起评判讨论 | 发起工具名称、授权及重复讨论合并规则待决定 |
| D06 | 实际启动讨论时，按当时整个应用的主世界 Agent 成员名单固定首轮席位，不按任务筛选；为成员创建 fork 并提供主题及主要参与方 | 排队期间新加入的成员可被纳入；启动后新增成员不加入本场。成员资格及会话快照截取时点待细化 |
| D07 | fork 基于原 Agent 配置与当前上下文，但只开放只读业务工具及讨论所需工具 | 不直接复制原 Agent 的全部写入权限；SDK 分叉与资源隔离须分别验证 |
| D08 | fork 在讨论房间投票；可投“支持 X”或“无建议”。无建议既可表示无关或没有相关上下文，也可表示不支持任何固定候选方案 | Q12 扩展原先仅表示无关的定义，不新增“均不支持”票型；不能把失败或未投票算作无建议 |
| D09 | 本轮席位均提交有效票后，支持票唯一最多且至少有一张支持票的方案获胜，不要求过半；第一轮最高票平票时补充讨论并重投一轮，仍平票交用户；全员无建议直接交用户；缺票限时等待，超时交用户 | 系统接收并记录用户裁决后迟到票不覆盖；两轮候选方案固定，同轮不改票，第二轮独立计票 |
| D10 | 讨论新增上下文不自动写回原 Agent；只向 @ 的主要参与方主动通知最终结果，其他原 Agent 可在后续主动读取 inbox 变化时获知结果并协调 | Q12 明确后续主动读取路径；讨论和答询过程仍不注入原会话。主动通知与 Agent 自行读取分开 |
| D11 | 裁决形成后，super agent 登记决定和任务安排，将触发讨论的 @ 标为已裁决，并通知主要参与方 | 不直接修改代码或运行任务命令，不改判赢家；不承担自动判断主世界变化是否使裁决失效的职责 |
| D12 | 严格保持原 Agent 对讨论过程无感知，允许另建独立答询 fork | 分身回答基于指定快照，不代表原 Agent 当前承诺，也不能凭新推理证明其历史动机；来源快照按 D40，答询协议继续细化 |
| D13 | 开始讨论时，整个应用全部主世界 Agent 在可控执行边界暂停；讨论 fork 投无建议后，对应原 Agent 可继续工作；支持票对应原 Agent 等到协调状态与结果通知写入完成后恢复 | 首轮无建议者不参与第二轮，也不因第二轮重新暂停。宿主控制暂停，不注入讨论过程、不撤销已执行操作 |
| D14 | 按主世界 Agent 身份分配投票席位，每个身份每轮一票；讨论和答询等临时分身不新增席位 | 同轮第一张被系统接受的有效票固定，重试不重复计票，不同内容不覆盖；首轮名单在实际启动时固定，第二轮按首轮支持票者派生 |
| D15 | 平票后的第二轮仅首轮投支持票的讨论 fork 参与，接收第一轮投票汇总及支持票理由，省略无建议票逐条内容；首轮无建议者不参与、不注入第二轮补充上下文 | 用户最新修正替换此前“无建议者也参与并接收汇总”。原始投票记录仍保留；不向原 Agent 注入讨论内容 |
| D16 | 全部席位均投无建议时，报告未形成裁决，直接交用户处理；各原 Agent 按无建议规则解除本讨论施加的暂停 | 最新暂停规则替换此前“主要参与方保持暂停”的附带约定。不自动重投、不产生默认赢家；释放暂停不表示批准争议请求，缺票不等于无建议 |
| D17 | 缺票时限时等待，仍缺票则交用户处理；用户裁决被系统接收并记录前，缺票补齐可取消对应询问并恢复计票 | 保留已有票及缺席状态；无建议者的原 Agent 可继续工作，支持票及尚未投票者的原 Agent 保持暂停。等待时长及具体取消流程待细化 |
| D18 | 以“系统已接收并记录用户裁决”为生效分界；此后迟到票只留档，不自动推翻用户决定 | 用户裁决提交与补票触发的询问取消必须互斥；若询问已取消，拒绝过期提交并明确提示。具体存储与并发实现待设计 |
| D19 | 只要求支持票唯一最多，不要求超过支持票总数或全部席位的一半 | 无建议不支持任何方案，也不增加胜出门槛；缺票仍走等待与用户处理流程，不能按部分票直接宣布赢家 |
| D20 | super agent 负责决定和任务安排，以及相关 @ 消息的状态更新与主要参与方通知 | 协调状态及主要参与方通知写入完成后释放本讨论暂停；通知读取与任务完成独立跟踪，不回写完整讨论过程 |
| D21 | 决定和任务安排登记后，触发讨论的 @ 从讨论中变为已裁决，关联裁决和后续任务；实际执行结果与读取状态单独跟踪 | 不等代码执行完成才结束争议协调，不因该旧消息重复触发讨论；已裁决不等于任务完成、通知送达或参与方已读 |
| D22 | super agent 不能自行改判；当前设计不增加裁决语义失效的自动检测、暂停应用或自动重议流程 | 最新修正撤销此前“失效时暂停应用”的专门机制；协调记录的写入失败、去重和重试仍是独立的工程问题 |
| D23 | 在本应用的协作决策中，以用户要求为最高优先级；Agent 票决及 super agent 的判断不得覆盖适用于当前事项的用户要求 | 用户明确改变要求时，不再应用与其冲突的旧裁决；遵循用户要求不是 super agent 自行改判 |
| D24 | 后续问题由 Agent 自行发现并主动 @ 相关 Agent，沿用普通消息及冲突讨论流程 | 替换此前“因失效自动重开一次”的机制；不设置专用失效重开计数、分身重建或升级用户分支 |
| D25 | 第一轮各讨论 fork 独立判断并提交投票与理由，投票前不互相交流或查看其他分身的本轮意见 | 平票后才向第二轮参与者注入首轮汇总及支持票理由；保留各自来源上下文和已允许的证据查询、独立答询能力 |
| D26 | 发起讨论时固定候选方案，由发起者在结构化主题中列明并引用相关方原始主张；两轮均在同一集合内投票 | 投票分身不能临时新增或改写方案；方案 ID 和正文含义保持一致。所有方案均不支持时投无建议 |
| D27 | 所有候选均不支持时选择无建议，沿用无建议的计票、提前恢复和退出第二轮规则；后续由原 Agent 读取消息变化后自行发起协调 | 不引入新的否决票或特殊重议机制，不把无建议算作对获胜方案的认可；后续仍沿用普通 @ 与冲突入口 |
| D28 | 第二轮也独立判断并投票；参加者读取首轮汇总和支持票理由后，各自重新评估固定候选方案 | 不增加互相追问或自由辩论阶段，不公开其他分身的第二轮实时意见；既有证据查询与独立答询能力仍保留 |
| D29 | 同轮投票被系统接受后不允许改票；进入第二轮的合法席位重新投票，第二轮单独计票 | 相同请求重试幂等，不重复计数、不重复触发释放；首轮旧票保留记录，不累加到第二轮，也不替代第二轮缺票 |
| D30 | 决定、任务安排和原 @ 已裁决状态保存，且主要参与方结果通知写入 inbox 后，宿主才解除本讨论剩余暂停 | 计票结束本身不放行；不要求提前标已读，不解除用户停止或其他独立阻塞。无建议者仍按提前恢复规则处理 |
| D31 | 应用内允许多场讨论并行，各场独立维护成员席位、分身、轮次、投票和暂停关系；并发上限可配置，第一版默认两场 | 等待用户的讨论仍占名额；同一原 Agent 只有解除所有相关暂停及其他独立阻塞后才恢复。跨讨论协调写入顺序待细化 |
| D32 | 并行讨论上限可配置，第一版默认同时最多两场；超额请求排队，实际启动时才施加该场暂停 | 等待用户继续占名额，不因排队提前暂停全员；动态修改上限与排队取消等细节待确认 |
| D33 | 等待用户处理的讨论继续占用并发名额，直到讨论结束 | 两场均等用户时后续请求继续排队；收到迟到结果后在原有名额内恢复处理，不因询问用户而释放名额或重复占位 |
| D34 | 首轮成员名单在实际取得并发名额并启动讨论时固定；之后新增成员不加入本场 | 不在入队时锁定名单，不因运行期间新增成员而追加席位。成员退出、停止或会话不可恢复的资格与失败处理仍需细化 |
| D35 | 讨论取得名额并固定成员后，先请求全部原 Agent 暂停；确认名单内全员到达可控边界、各自完整可恢复位置已记录后，才创建讨论 fork 并开始评判 | 不边暂停边创建分身或投票；不保证各会话位置属于同一时刻，不自动冻结文件。正常执行收尾按 D36；SDK 接入及分叉失败处理待细化 |
| D36 | 正常暂停等待当前执行成功、失败或超时并完成收尾，记录结果后阻止原 Agent 继续推进，再确认暂停和可恢复位置；第一版不增加讨论启动专用的自动退让、重新排队和重试机制 | 工具超时需由执行层落实；调用方超时不等于底层操作停止，不回滚已发生副作用。模型等待、进程失联和收尾失败纳入通用运行时故障恢复设计，不能无限等待或算作无建议；具体处理仍待确定 |
| D37 | 全员暂停确认后、讨论分身开始读取前，为本场讨论保留固定的只读代码文件快照；第一轮和第二轮使用同一版本 | 原 Agent 恢复后继续修改工作目录，不改变本场快照。未提交内容按 D38、范围原则按 D39；创建与清理实现待细化；不自动检测裁决语义失效，不把会话分叉视为文件快照 |
| D38 | 纳入快照范围的文件以全员暂停后磁盘上的实际内容为准，包含未提交修改、新建文件和删除状态，不要求先提交 Git | 不仅从最近一次 Git 提交还原，也不要求修改用户的提交历史或暂存区；范围原则按 D39，匹配规则及快照实现待细化。未保存到磁盘的编辑器内容不属于本规则定义的磁盘状态 |
| D39 | 快照覆盖整个项目的工作文件，包括源码、测试、文档和必要配置，不由发起 Agent 自行筛选相关文件；统一排除依赖目录、构建缓存、Git 内部数据、应用运行状态和凭证文件，规则由项目配置管理 | 文件供分身按需读取，不将整个项目自动注入上下文；确切匹配规则、例外、体积限制和访问控制实现仍待细化 |
| D40 | 答询分身从该身份在本场讨论暂停时已记录的原会话位置派生，文件读取使用本场固定快照；不采用原 Agent 恢复后的新上下文，也不从已含本轮投票意见的讨论分身派生 | 可以基于固定材料重新推理，回答不回写原会话、不代表原 Agent 最新承诺；复用与提问者隔离按 D41，答询层级按 D42，次数预算按 D45 |
| D41 | 同一讨论分身向同一目标连续追问时，复用其专属答询会话；按讨论房间、提问者席位、目标身份隔离，不同提问者不共享后续问答上下文 | 答询来源仍按 D40 固定，不新增投票席位；会话复用不等于要求进程一直存活。跨轮复用按 D43、次数预算按 D45、创建时机按 D46；并发和清理细则仍待确定 |
| D42 | 第一版仅允许讨论分身发起一层答询；答询分身不能继续向其他分身询问或自行创建分身 | 答询分身基于固定来源、获准读取的本场文件及专属问答作答；信息不足时说明缺口，交提问者决定是否另问其他目标。不能绕过工具权限形成递归答询；次数预算按 D45 |
| D43 | 进入第二轮的合法参与者继续复用首轮对同一目标的专属答询会话，保留此前问答；来源上下文与文件版本仍固定为本场快照 | 不共享其他提问者的问答，不获取其他分身第二轮实时意见；答询分身没有投票权，首轮无建议者不恢复投票资格。保留历史可能延续首轮判断倾向，第二轮仍由讨论分身独立重新投票 |
| D44 | 单次答询超时或失败时，工具向提问者返回明确失败结果，由讨论分身基于已有证据继续判断、查询或显式投票 | 不把答询失败自动转换成无建议，不因一次辅助查询失败直接终止整场或询问用户；未按本轮期限提交有效票时仍走既有缺票规则。次数预算按 D45；重试和迟到答复细则待定 |
| D45 | 每个投票席位每轮的答询次数上限可配置，第一版默认 5 次；对所有目标的首次询问与追问合计，已执行但失败的请求也计入，同一请求的幂等重传不重复扣减 | 用尽后返回额度已用尽，由提问者基于已有材料继续判断；不代投、不直接询问用户、不延长投票期限。第二轮按该轮席位独立计次，会话复用不沿用首轮已用次数；5 次为后续实际任务验证的初始值 |

| D49 | 正常运行中的主世界 Agent 收到新消息后，在可控执行边界仅接收三档状态及未读数量的轻量提醒，正文通过 view_inbox 拉取；有未读 @ 时引导优先查看并判断是否调整行动 | 不自动注入全部正文，不中断正在执行的工具，不因提醒发出而标已读。提醒合并与频率按 D50，自然空闲唤醒按 D51，暂停积压按 D53；异常恢复另定，不改变原 Agent 对讨论过程无感知的规则 |
| D50 | 运行中提醒由新消息触发，同一可控执行边界前到达的消息合并提醒；成功提醒后没有新消息，就不重复提醒同一批未读 | 未读记录继续保留，后续新消息仍触发提醒；不能只以未读数量是否变化判断有无新消息。Agent 忽略提醒后不持续催读；提醒失败补送、投递确认及重启恢复细则待定 |

## 4. 状态和数据的分界

以下是用于讨论的概念分界，不是已冻结的数据库表或 TypeScript 接口。

| 概念 | 负责表达什么 | 不能与什么混同 |
| --- | --- | --- |
| 主世界 Agent | 稳定身份、任务、配置、原 SDK 会话关联 | 一次运行的进程 PID |
| 主世界状态 | 任务归属、已接受决定、相关代码和执行结果 | 某个 Agent 的上下文或口头承诺 |
| inbox 消息 | 发送者、接收范围、正文、线程、@ 目标、顺序标识 | 用户指令；其他 Agent 的文本不能冒充用户授权 |
| 接收者读取进度 | 某个 Agent 已读取到哪些消息 | 消息已完成处理或相关操作已成功 |
| 讨论主题快照 | 争议是什么、可选方案、证据、参与方、依据的版本 | 持续变化的整个主世界 |
| Agent fork 快照 | 原会话在某个可恢复位置的上下文与明确的配置版本 | 进程内存复制、正在生成的推理、正在运行工具的完整现场 |
| 讨论会话 | 与原会话隔离的新增对话、证据及投票 | 原 Agent 的工作上下文 |
| 裁决与应用记录 | 票决结果、应用条件、是否已更新主世界 | 单独一条“某方案赢了”的聊天消息 |

### inbox 三档状态

**Q33 已确认**：“未新增 / 新增消息 / @ 消息”是按接收 Agent 未读消息派生的提示，不是全部消息的互斥业务状态。普通未读和未读 @ 可以同时存在，分别保留，不因优先显示 @ 而丢弃普通消息。

| 当前接收者的未读情况 | 提示 |
| --- | --- |
| 有未读且 @ 当前 Agent 的消息 | @ 消息 |
| 无未读 @，但有普通未读消息 | 新增消息 |
| 没有未读消息 | 未新增 |

例如两条未读 @、五条普通未读时显示“@ 消息”；确认两条 @ 已读后显示“新增消息”。已读但未处理的事项由任务与裁决状态跟踪，不继续占用未读提示。“未新增”只说明没有未读消息，不说明所有任务已完成。分页、过滤和跨线程读取时如何表达读取进度仍待决定。

**Q32 已确认**：`view_inbox` 只负责拉取，接收 Agent 按消息 ID 显式确认后才标为已读；不能因查询已完成或消息准备送入 SDK 就清空未读。确认由 Agent 完成，不增加用户操作。该确认是应用记录的已读声明，不等于证明模型已理解内容或已经执行任务；已处理、已裁决及任务完成继续独立跟踪。未确认消息可能再次返回；是否提供独立工具、合并到后续工具调用、批量确认及游标压缩方式均待接口设计。

必须讨论以下时点的区别：消息入库、送入 SDK、模型读取、模型决定处理、操作完成、结果确认。尤其不能因为“已导入 message”就清空尚未确认的处理状态。

`view_inbox` 本身不能让未运行的 Agent 感知消息。轻量通知、正文拉取、会话续跑、已退出进程的恢复属于不同环节。

**Q36 已确认**：仍登记在应用中的主世界 Agent 自然空闲或正常结束本次运行后，普通新消息和 @ 都可触发宿主自动恢复对应原会话，开启一轮 inbox 检查。先提供轻量提醒，引导调用 `view_inbox`，再由 Agent 判断后续动作；自动唤醒不等于重跑旧任务、恢复旧操作或直接执行消息要求。用户显式停止、讨论暂停及其他独立阻塞不能被消息解除；这些状态下消息仍保存，积压提醒按 Q38。异常退出和原会话无法恢复进入故障恢复设计，不因本规则默认新建无历史会话或无限重试。并发唤醒按 Q37，SDK 接入与生命周期恢复仍需验证。

**Q37 已确认**：每个主世界身份同时只允许一个执行实例，宿主按身份统一调度并合并唤醒请求。正在启动时，新到消息继续存入 inbox，由该次唤醒的实例检查；已经运行时，按既定可控边界提醒，不因每条消息另起实例。暂停期间也不能以创建第二个实例绕过阻塞。讨论与答询 fork 是不同的会话分支，不属于重复主世界执行实例，但继续受各自房间、席位和预算约束。启动与退出交界的消息补送、去重和崩溃后的实例归属需在实现中保证，不能因“合并唤醒”丢弃新消息。

**Q38 已确认**：暂停期间的新消息先保存，不唤醒或注入暂停的原会话。所有相关讨论暂停、用户停止等阻塞各自被合法解除后，对积压且尚未成功提醒的新消息合并补送一次轻量提醒，正文继续通过 `view_inbox` 拉取，接收 Agent 显式确认后才标读。只解除一场讨论而另一场仍暂停时不能补送；不能由新消息自动解除用户停止。暂停前已经成功提醒的旧消息不因恢复再次催读。补送沿用消息接收范围，不向非主要参与方自动追加裁决结果或完整讨论内容。

### 运行中的轻量提醒

**Q34 已确认**：正常运行中的主世界 Agent 收到新消息时，宿主在可控执行边界注入轻量提醒，包含三档状态和未读数量；未读 @ 存在时，引导优先调用 `view_inbox` 并考虑是否调整当前行动。例如：“Inbox：2 条未读 @，5 条普通未读。请优先查看 @ 消息，并判断是否需要调整当前行动。”正文仍由工具按需返回，不将所有正文自动灌入工作上下文。

提醒不能中断正在执行的工具，也不能推进已读状态；读取和显式确认仍按 Q32 处理。运行中提醒不授权向因讨论暂停的原会话注入讨论过程，也不唤醒已被用户停止的 Agent。提醒频率及合并方式按 Q35，自然空闲唤醒按 Q36，其他生命周期下的处理继续细化。SDK 提醒接入仍需验证，本文不将 Hooks 提示等同于已经实现的调度保证。

**Q35 已确认**：只有新消息到达才触发运行中提醒，同一可控边界前到达的多条消息合并提醒。成功提醒之后，若没有新消息，不在后续每次工具结束时重复提醒同一批未读；未读记录不因此清除，Agent 后续仍可主动拉取。再次有新消息时仍应提醒，不能仅比较未读总数或三档状态来判断是否存在新增。该规则减少重复上下文，接受 Agent 忽略提醒后不被持续催读的代价。“成功提醒”的投递确认、失败补送及重启恢复另行设计，不将发送尝试直接等同于成功，也不承诺当前已有恰好一次投递能力。

## 5. 分叉讨论的预期流程

以下描述保留用户提出的主流程；带待决策标记的步骤不能直接编码成固定政策。

1. A @ B。B 在可控执行边界读取消息及必要上下文。
2. B 判断存在冲突，调用发起讨论工具，在主题中列明固定候选方案及相关方原始主张。工具登记请求和主要参与方；有并发名额时实际启动，否则排队且不暂停全员。
3. 实际启动时，按当时应用全部主世界 Agent 身份固定首轮名单，每个身份一个席位，不按任务筛选。宿主向名单内全部原 Agent 请求本场暂停；确认全员到达可控边界、各自完整可恢复位置已记录后，才创建讨论 fork 并开始评判。之后新增成员不加入本场；已有临时分身不增加席位。暂停请求发出不等于暂停成功；无法到达边界时的处理、已停止或已退出成员资格及具体分叉位置的取得方式仍待细化。
4. 全员暂停确认后、讨论分身开始读取前，宿主为本场保留固定的只读代码文件快照。fork 获取对应原 Agent 的上下文、只读业务工具和讨论工具，在隔离的会话中独立判断；本场两轮均读取同一文件版本，不因无建议者恢复工作而转读其新修改。第一轮不交换本轮意见，也不查看其他分身已提交的投票和理由。文件快照范围及创建机制仍待细化。
5. 需要补充证据时查询已有记录；需要推理答询时，从目标身份在本场暂停时已记录的原会话位置另建独立答询 fork，读取本场固定文件快照。不采用原 Agent 恢复后的新增上下文，也不从带有本轮投票意见的讨论分身派生。同一提问者对同一目标的连续问答复用专属会话，不同提问者隔离。第一版只保留一层答询，答询分身不能自行继续询问或创建分身；信息不足时返回缺口，由提问者决定是否另问其他目标。禁止向原 Agent 本体注入讨论问题；具体接口与预算待设计。
6. fork 对明确的方案 X 投支持票，或在符合条件时投无建议。投无建议后，对应原 Agent 可继续工作；投支持票的原 Agent 等待最终结果。本轮席位均提交有效票后，至少有一张支持票且支持票唯一最多的方案获胜，不要求过半；第一轮最高票平票时，补充讨论再投一轮，仍平票交用户。全部席位均投无建议时直接交用户、不自动重投，各原 Agent 按无建议规则解除本讨论暂停。缺票限时等待，超时交用户；用户裁决被记录前，缺票补齐可取消对应询问并恢复计票；此后迟到票只留档。
7. super agent 按既定裁决登记决定和任务安排，将触发讨论的 @ 从讨论中标为已裁决，并关联裁决及后续任务；不直接修改代码或运行任务命令，不自行改判。用户要求保持最高优先级。当前不增加裁决语义失效的自动检测与重议流程。实际执行结果和读取状态单独跟踪；去重与提交协议仍待设计。
8. super agent 将主要参与方最终结果通知写入 inbox。决定、任务安排、原 @ 状态和这些通知均已保存后，宿主才解除本讨论剩余暂停；具体代码工作由负责的原 Agent 完成。讨论的完整新增上下文不回写原 Agent，不向非主要参与方自动注入结果；它们后续可主动读取 inbox 变化。讨论记录清理政策待决定。
9. 原 Agent 在后续读取 inbox 变化或执行工作时发现问题，主动 @ 相关 Agent。若接收方判断存在冲突，再按普通讨论入口处理，不由宿主自动判定旧裁决失效并重开。此前投无建议不禁止原 Agent 后续重新提出问题。

### 候选的结构化讨论主题

建议至少讨论以下字段，不视为已确定的接口：

- `discussionId`、所属代码任务、触发消息 ID、发起者、主要参与方。
- 明确的争议问题、目标、用户约束、每个方案的稳定 ID 和内容。
- 证据引用、相关文件版本、任务状态版本、已发生的操作。
- 成员集合及每个成员对应的原 Agent ID、原 SDK 会话 ID、分叉位置、配置版本。
- 主题版本、投票规则版本、截止条件、结果和主世界应用记录。

**Q11 已确认**：候选方案由发起者在讨论开始时列明并固定，引用相关方原始主张；第一轮与第二轮使用同一集合，不允许分身在投票期间新增、删除或改写方案。“支持 X”指向稳定的方案 ID 和内容，不能只投给某个 Agent 的名字或在同一 ID 下悄悄更换方案。

各方案描述如何引用原消息、如何校验必填字段等接口细节仍待设计。**Q12 已确认**：有相关上下文但不支持任何候选方案时，也投无建议；保留两种票型，不新增均不支持或否决票。这扩展了无建议的语义，不意味着把该 Agent 认定为事实上无关。

无建议在计票中不支持任何方案，也不阻止其他方案按既定规则胜出；对应原 Agent 可继续工作，首轮无建议者不参加第二轮。裁决后 inbox 消息状态发生变化，原 Agent 后续读取后可自行 @ 并发起新的协调；不自动代它触发讨论，也不把此前无建议视为认可胜出方案。

### 第一轮独立判断（Q10 已确认）

- 各讨论 fork 基于主题、各自继承的上下文和证据独立判断，提交选择与显式理由。第一轮不安排分身间的自由交流，不向它们公开其他分身本轮的选择和理由。
- 每个分身的原 Agent 上下文可以包含争议产生前已有的讨论；独立判断不等于所有分身拥有完全相同的信息，也不意味着它们在统计意义上相互独立。
- 已确认的只读证据查询和独立答询 fork 机制仍保留，但不能通过答询或其他工具绕过第一轮投票意见的隔离。查询与答询的具体范围待后续定义。
- 只有首轮平票才进入补充轮，向参与第二轮的首轮支持票者提供首轮汇总及支持票理由。首轮无建议者不进入第二轮。

候选方案按 Q11 在发起时固定；Q13 已确认第二轮也独立判断，不另设分身间自由交流阶段。

### 平票后的补充讨论（Q8.1 已确认）

1. 第一轮最高票平票时，补充讨论并再投一轮；第二轮仍平票则交用户裁决，不自动进入第三轮。
2. 收集第一轮投票结果和支持票的理由，作为补充讨论的新增上下文。理由指 Agent 为投票显式提交的说明，不要求访问模型隐藏推理。
3. **Q6R.1 最新修正已确认**：首轮投无建议的讨论 fork 不参与第二轮；第二轮只包含首轮投支持票的席位。不应因首轮无建议者没有第二轮投票而判缺票或重新唤起它。
4. 新增内容只注入参加第二轮的讨论 fork，不写回原 Agent；其对应原 Agent 继续等待最终结果。首轮无建议者的原 Agent 继续工作，不因本次第二轮而重新暂停。
5. 第二轮参与者收到第一轮投票汇总及支持票理由，省略无建议票的逐条内容。此前“所有讨论 fork，包括无建议者，都接收补充上下文”的约定被本次修正替换。
6. 例如 A′ 支持 X、B′ 支持 Y、C′ 无建议：仅 A′、B′ 进入第二轮并收到汇总及 A′、B′ 的理由；C′ 不进入第二轮、不接收补充上下文，原 C 继续工作。原始 C′ 无建议票保留为第一轮记录，不伪装成第二轮票或缺票。
7. **Q13 已确认**：第二轮参加者分别读取首轮汇总与支持票理由，独立判断后重新投票。不增加自由交流、互相追问或实时查看其他分身第二轮意见的阶段。第一轮证据查询与独立答询能力继续按原边界使用，不得借此获取其他分身本轮投票意见。

第二轮沿用首轮固定方案，不允许修改选项；参加者仍使用支持 X 或无建议的票型，选择无建议时沿用恢复原 Agent 的规则。Q14 已确认同轮不改票，第二轮重新投票；票理由的结构和汇总展示方式仍待细化。计票按轮次及该轮参与席位进行，第二轮只等待其自身席位，不累加第一轮旧票。

### 胜出门槛（Q8.4 已确认）

本轮全部席位提交有效票后，按各方案收到的支持票计数。只要有至少一张支持票，且某方案的支持票严格多于所有其他方案，即判该方案胜出。不要求支持票过半，不要求全部席位过半，无建议不增加门槛。

例如 X 三票、Y 两票、Z 两票、无建议三票，X 胜出。最高支持票并列走平票规则；所有席位均无建议走全员无建议规则；存在缺票走限时等待规则。每轮投票独立记录与统计，第二轮不复用首轮票充当新票；请求字段和存储协议仍待设计。

### 同轮票固定与跨轮重投（Q14 已确认）

系统接受的第一张有效票固定下来，同一身份在同一轮不能用后续不同内容覆盖。相同请求重试应返回既有结果，不重复计票或重复触发释放原 Agent。未被接受的无效请求不占用席位；具体验证字段后续设计。

首轮平票后，仅有资格进入第二轮的身份重新投票，可在固定候选中重新选择或投无建议；此为新一轮判断，不是修改首轮记录。第二轮计票不累加首轮票，也不能用首轮票补齐第二轮缺席。

### 全员无建议（Q8.2 已确认）

全部席位均明确投无建议时，直接交用户处理，报告未形成裁决。不自动检查并重投，也不套用最高票平票的补充讨论规则。按最新暂停规则，各原 Agent 在投无建议后解除本讨论暂停；这一点替换此前“主要参与方保持暂停”的附带约定。解除暂停不等于批准原争议请求。未响应或失败的席位不能被当成无建议。

按 Q12 扩展后的定义，无建议也可表示不认可任何固定候选；因此主要参与方投无建议不应仅凭这一事实判为快照异常。全员无建议仍报告没有形成方案支持并交用户，不自动修复或重投。

### 缺票超时与迟到结果（Q8.3 / Q8.3a 已确认原则）

- 设置有限等待期限，期满仍缺票则交用户处理，保留已经收到的票并标记未响应或失败的席位。投支持票或尚未投票者的原 Agent 保持暂停；已投无建议者的原 Agent 可继续工作。
- 不把缺票自动转换为无建议，也不因到期就按已收到的部分票宣布赢家。
- 用户补充要求：如果后续返回结果，则取消询问用户。因此超时转交用户不能简单等同于永久拒收迟到结果或立即销毁所有未完成的分身。
- **Q8.3a 已确认**：以“系统已接收并记录用户裁决”为分界。此前缺票补齐可取消缺票询问并恢复计票；此后保留用户裁决，迟到票只留档，不自动覆盖。
- 用户提交与补票取消同时发生时，只能有一个状态转换成功。若系统先成功记录用户裁决，后续票不改变裁决；若缺票询问先成功取消，过期用户提交不能再被当作该询问的有效裁决，需要明确提示。单纯点按钮、输入中的内容或尚未被系统接受的请求不等于已记录裁决。
- **后续待细化**：等待时长与起算点；部分补票时的进度展示；取消询问时的提示文案与记录结构；互斥状态转换、去重及崩溃恢复的实现。

“取消缺票询问”不等于“已经产生最终赢家”：补齐后仍可能平票或全员无建议，需要进入相应规则。若仍有缺票，不能按部分票宣布赢家。具体持久化状态转换的实现仍待设计。

### super agent 的职责（Q9 已确认）

super agent 更新决定和任务安排，更新 inbox 中触发讨论的 @ 消息状态，并通知主要参与方。它不直接承担代码修改或任务命令执行，相关操作由负责的原 Agent 在恢复后执行。

**Q9.1 已确认**：决定和任务安排登记后，原 @ 从“讨论中”变为“已裁决”，关联裁决与后续任务，不再因这条旧消息重复触发讨论。不需要等待任务执行完成才结束此次争议协调。

后续任务的待执行、执行中、成功或失败单独跟踪；读取状态单独记录，不能因为产生裁决就假定参与方已读。已裁决也不等于通知已经送达。状态字段的具体编码、被否决请求如何关联后续安排、通知格式及恢复顺序留待讨论。

**Q9.2 最新修正**：保留 super agent 不能改判赢家的约束，移除“检测裁决语义失效并暂停应用”的专门职责。当前设计没有定义可靠判断“主世界变化导致裁决失效”的机制，不应在代码中假定该能力存在。

**Q9.3 已确认的优先级原则**：以用户要求为最高优先级。若用户已明确改变当前事项的要求，Agent 投票与 super agent 均不得覆盖该要求；与用户要求冲突的旧裁决不再应用。遵循用户的新要求不是 super agent 自行选择另一个赢家，也不需要让 Agent 投票批准用户要求。

**Q9.3a / Q9.3b 已撤销，不再作为待决策项**：不实现因裁决失效而自动重开一次、再次失效交用户的流程，相应的重开次数、重新邀请成员及分身重建问题一并移除。Agent 后续自行发现问题后主动 @ 相关 Agent，沿用现有消息与冲突讨论机制。

这项范围收缩不取消平票后的第二轮规则，也不取消消息去重、并发写入、通知恢复等工程要求；它不承诺系统会自动发现所有过时判断。

### 全员暂停与按票释放（Q6 修正已确认）

**Q20 已确认**：取得讨论名额并固定名单 → 请求全员暂停 → 确认全员到达可控边界且各自完整可恢复位置已记录 → 创建讨论 fork、开始独立判断和投票。不能在其他成员尚未完成暂停时，让已暂停成员的讨论 fork 提前投无建议并恢复原 Agent。该顺序不承诺跨会话的同一时刻快照或文件系统冻结；记录位置所需的 SDK 接入仍待验证。

**Q21 已确认**：在工具均有超时的设计前提下，正常路径等待当前执行成功、失败或超时并收尾，记录结果后暂停，不增加讨论专用的退让重试流程。宿主必须阻止暂停请求之后的后续工具、Agent 自主重试或排队输入继续推进；具体 SDK 接入仍需验证。仅调用方停止等待而底层命令仍运行，不等于安全收尾；超时也不撤销外部副作用。模型等待、进程失联和无法收尾等异常进入通用运行时故障恢复设计，不在此处默认无限等待、强杀、跳过成员或升级用户。该决定不改变讨论开始后已确认的缺票与用户裁决规则。

用户明确修正此前设计，当前规则为：

1. 讨论开始时暂停整个应用全部主世界 Agent，不按主要参与方筛选；讨论和答询分身保持所需的运行能力，不属于要一并停掉的原 Agent。
2. 某身份的讨论 fork 投无建议后，解除该原 Agent 由本讨论施加的暂停，让它继续工作；无需等全部投票返回。
3. 投支持票的原 Agent 在投票后仍等待；按 Q15，必须等决定、任务安排和原 @ 状态保存、主要参与方结果通知写入 inbox 后才释放本讨论暂停。未投票或失败不能冒充无建议来提前释放。
4. “是否为主要参与方”决定最终结果的主动通知范围；“当前投票是否为无建议”决定提前释放资格。非主要参与方投支持票也须等待，但不因此自动向其原会话注入讨论内容；其放行可由宿主调度完成，后续可自行读取 inbox 变化。
5. 原 Agent 的上下文无感知要求保持：暂停与恢复通过宿主执行控制完成，不向原会话注入讨论过程。恢复本讨论的暂停不代表可以解除用户显式停止或其他独立阻塞。

**Q6R.1 已确认**：首轮无建议的讨论 fork 不参与第二轮，不接收第二轮补充上下文；对应原 Agent 继续工作，不因第二轮而重新暂停。此前“无建议者也必须参加第二轮”的要求已被用户明确修正。第二轮仅首轮投支持票者参加，其原 Agent 继续等待最终结果。

退出第二轮不意味着必须立即销毁分身或删除记录，进程与记录的清理时机另行设计。后续 Agent 主动 @ 引起的讨论沿用普通入口，不存在额外的裁决失效自动重开通道。

**Q15 已确认**：先保存决定、任务安排及原 @ 已裁决状态，再确保主要参与方结果通知已写入 inbox，之后由宿主解除本讨论剩余暂停。只有计票结果、尚未完成这些写入时不能提前放行；也不要求原 Agent 在恢复前已读，不伪造读取进度。写入失败、部分成功或崩溃后如何恢复，属于后续提交与可靠性设计。

Q16 已确认允许多场讨论并行，暂停按讨论分别管理，具体见下节。暂停失败以及恢复调度的实现仍待细化。全员暂停只能约束应用可控制的执行，不能声称文件系统、外部用户及已发出的外部操作一并被冻结。

### 并行讨论与暂停归属（Q16 已确认）

- 允许一场讨论尚未结束时启动另一场讨论，各场独立维护分身、参与席位、候选方案、轮次和投票。Q17 已确认并发上限可配置，第一版默认同时最多两场。
- 超过上限的讨论请求排队，只有实际启动时才施加该场讨论的暂停；排队本身不暂停全员，也不提前创建整组讨论分身。排队请求的顺序、取消、重启恢复及正式启动时的主题和快照处理仍待设计。
- 默认上限约束的是并行讨论场数，不代表单个讨论中分身数量或答询调用量已有独立预算；这些资源预算仍待细化。Q18 已确认，等待用户处理的讨论继续占用名额，直到该讨论结束。
- 两场讨论都在等用户时，新请求仍排队。迟到结果补齐后取消询问并恢复计票，继续使用该讨论原先的名额，不重新竞争或重复占用名额。用户提交裁决也不等于立即跳过 Q15 的协调状态和通知写入收尾。
- Q19 已确认，首轮名单在实际取得名额并启动时固定。例如请求入队后 C 加入应用，只要 C 在启动时属于主世界成员，就纳入本场；启动后新加入的 D 不加入本场。第二轮仍只从本场首轮支持票者派生。
- 讨论名额与原 Agent 的暂停分别管理：即使全员无建议、原 Agent 均已解除本场暂停，该场等待用户处理的讨论仍占名额。结束、取消或错误终止时的名额回收和恢复协议待实现设计。
- 暂停必须归属于具体讨论，不能只用一个无来源的暂停布尔值。某原 Agent 在讨论 D1 投无建议，只解除 D1 的暂停；若 D2 仍要求等待，该原 Agent 不能恢复工作。
- 某场讨论完成 Q15 规定的写入后，也只能释放该场讨论的暂停。仅当所有相关讨论暂停都已解除，且没有用户显式停止等独立阻塞时，原 Agent 才恢复。
- 例如 A 同时受 D1、D2 暂停：D1 无建议、D2 支持 X，则 A 继续等待 D2；D2 完成决定、任务安排、@ 状态和通知写入后，若没有其他阻塞，A 才恢复。
- 一个讨论结束不得清除其他讨论的数据、投票或暂停关系；同一原 Agent 在不同房间的分身仍分别代表该房间的同一身份席位，不能混用票或消息。

重复暂停请求的去重、已因其他讨论暂停时如何取得新分叉位置、多个讨论更新同一任务安排的提交顺序及重启恢复，属于后续实现边界。不引入裁决语义失效的自动判定或自动重议。

## 6. 隔离与询问

### 原 Agent 无感知与主动答询

如果讨论 fork 直接向原 Agent 发消息，并要求原 Agent 推理回答，原 Agent 必然接收新输入或开启新一轮；这与“讨论对原 Agent 无感知”不能同时严格成立。通信协议名叫 A2A 并不能消除这个状态变化。

Q5 已确认选择“严格无感知，允许另建答询分身”。下面保留方案比较作为决策依据，不表示所有方案仍待选择：

| 方案 | 是否改变原会话上下文 | 能力与代价 |
| --- | --- | --- |
| 读取已保存的状态和证据 | 否 | 简单、可追溯；不能获得原 Agent 尚未表达或保存的判断 |
| 从原会话再创建独立答询 fork | 否，前提是分叉配置正确 | 可对问题推理；额外成本，回答只代表所用快照，不是原 Agent 本体的承诺 |
| 向原 Agent 本体询问 | 是 | 能获取本体的最新回答，但必须明确放宽“无感知”要求 |
| 只允许讨论开始时的快照 | 否 | 快照一致性较清楚，但无法补充之后出现的证据 |

**已确认的方向**：严格保持原 Agent 对讨论过程无感知，允许从原会话的明确位置另建独立答询 fork。原 Agent 不接收问题、不因答询开启新一轮，其会话不加入答询内容。最终结果仅主动通知主要参与方；Q12 明确其他原 Agent 后续可以通过主动读取 inbox 变化获知结果，此路径不等于回写完整讨论过程。

答询分身的回答是基于其快照形成的判断，不能当作原 Agent 当前的承诺，也不能当作未记录的历史动机的证明。

**Q25 已确认**：答询分身使用目标身份在本场暂停时已记录的原会话位置，并读取本场固定文件快照。即使原 Agent 已因无建议而恢复工作，后来创建的答询分身仍从本场固定来源派生；不能采用原 Agent 之后新增的上下文，也不能从含本轮投票意见的讨论分身派生。固定来源允许答询分身结合问题重新推理，但不赋予它新增投票席位，也不改变独立判断和原会话无感知要求。

**Q26 已确认**：同一讨论分身对同一目标的连续追问复用一个专属答询会话，以“讨论房间＋提问者席位＋目标身份”区分问答上下文。例如 A′、B′ 都向 C 答询，各自得到独立的 C 答询会话；两者均从本场固定的原 C 位置派生，但不共享后续问答，A′ 的追问不会进入 B′ 所用答询会话。不能通过共用有状态答询会话或答复缓存绕过该隔离。跨轮复用按 Q28、创建时机按 Q31，进程保持及回收仍待细化。

**Q27 已确认**：第一版只保留一层答询，由讨论分身组织信息收集。答询分身使用固定来源上下文、本场获准读取的文件及该提问者的问答记录作答；不能继续询问其他分身或自行创建分身。如果需要其他身份掌握的信息，说明缺口并返回给提问者，由提问者决定是否另行答询。此权限边界须由宿主工具授权落实，不能仅靠提示词约束，也不因此开放向原 Agent 本体发消息的通道。

**Q28 已确认**：第二轮合法参与者继续使用自己首轮对同一目标的专属答询会话，可接着此前问答追问。来源上下文和文件版本保持本场固定快照，不刷新为原 Agent 最新状态，也不混入其他提问者问答或其他分身第二轮实时意见。保留首轮问答可能延续既有判断倾向；第二轮选择仍由讨论分身独立重判，答询会话不新增投票权。首轮无建议者依然不进入第二轮，不因答询会话存在而重新获得资格。

**Q29 已确认**：单次答询超时或失败时，工具向提问者返回明确失败结果，表达本次证据未取得；由讨论分身评估已有材料，决定继续查询或自行投支持票/无建议。系统不能把辅助答询失败伪装成有效答案、替提问者投无建议，或仅因本次失败直接终止讨论、询问用户。继续查询仍受本轮投票期限及后续预算规则约束；若最终没有有效投票，照常进入缺票处理，不能因答询失败自动延期。失败后的重试与迟到答复处理继续细化。

**Q30 已确认**：为每个投票席位每轮设置可配置答询次数上限，第一版默认 5 次。向不同目标的首次询问与追问共同计数，已接受并执行的失败请求也占一次，同一逻辑请求的幂等重传不重复扣减。例如 A′ 向 B 问两次、向 C 问三次后，本轮不能再发起新的答询。额度用尽返回明确结果，由 A′ 根据已有材料继续判断；不自动代投或询问用户，投票期限不延长。第二轮只为合法参与席位独立计次，即使复用首轮答询会话，也不能误用首轮计数；5 次是待实际任务验证的初始值。请求标识、并发扣减、未执行请求及重启恢复的计数实现继续细化。

**Q31 已确认**：专属答询分身按需创建。讨论启动时先保留目标身份的固定原会话位置及本场文件快照，某提问者首次实际询问该目标时才创建其专属答询会话，后续追问及合法跨轮追问按既定规则复用。不为未发生询问的提问者—目标组合预建分身。首次询问承担启动延迟，但分身来源仍为本场固定位置；较晚创建不代表可以改用原 Agent 最新上下文。该规则不改变投票讨论分身的全员创建要求。并发首次创建的去重、创建失败、闲置进程回收及会话清理后续细化。

**尚未确认的细节**：优先查询已有事实的具体流程、答询创建失败及进程回收、失败重试与迟到答复、超时及其他资源预算、答复来源和版本字段，以及新证据的共享政策。任何共享不得绕过已确认的本轮投票意见和提问者问答隔离。

### 上下文只读不等于环境快照

**Q22 已确认**：全员暂停确认后、讨论分身开始读取前，为本场讨论保留固定的只读代码文件快照，两轮共用。原 Agent 恢复后修改工作目录，不影响本场讨论所读版本。固定的是本场文件证据，不会改写分身继承的历史上下文，也不要求暂停所有外部写入者；快照创建期间如何保证范围内文件一致仍需在实现中验证。讨论外的任务状态与外部服务不由此自动冻结，答询来源版本另按 Q25 固定。

**Q23 已确认**：快照范围内以暂停后磁盘实际内容为准，保留未提交修改、新建文件及删除状态，不要求 Agent 先提交 Git。例如已删除的文件不能因为旧提交中仍存在就重新出现在快照中；新文件不能仅因尚未被 Git 跟踪而遗漏。这不等于无条件复制工作目录全部内容，范围原则按 Q24。

**Q24 已确认**：以整个项目工作文件为范围，包含源码、测试、文档及必要配置，不由发起 Agent 只挑选它认为相关的文件。统一排除依赖目录、构建缓存、Git 内部数据、应用运行状态及凭证文件，规则由项目配置管理。纳入快照表示分身可按权限和需要读取，不表示把所有文件正文预先注入上下文；确切匹配方式、例外和大小限制仍待细化。

- fork 的会话分支不会自动冻结代码文件；若工具直接读取主世界工作目录，仍可能读到其他 Agent 刚修改的文件。实现需要确保讨论中的代码读取遵守本场固定快照，不能仅靠只读提示词保证。
- “继承配置”应理解为从原配置派生，再显式收窄权限；写入型 CLI 命令权限、hooks 和环境连接不能未经审查原样继承。允许 Bash 调用 CLI 时，文件只读仍须单独落实，不能仅由角色提示保证。
- 投票工具会写讨论房间状态，它是限定范围的允许写入，不应因此开放主世界修改权限。
- 只读提示词或工具名称不是完整隔离措施。固定文件快照要求已确定；采用独立目录、工作树或其他存储方式及访问控制仍需结合实现验证，不能把普通可变工作树自动视为只读快照。
- 不得把完整环境变量或凭证保存为可见的讨论配置快照。

## 7. 需要覆盖的失败与并发情形

本节列出后续必须有明确政策的情况；推荐处理不代表已获用户确认。

| 情形 | 风险 | 当前待确定的问题 |
| --- | --- | --- |
| 主 Agent 正在工具调用，分叉点尚未完整保存 | fork 只有部分上下文或缺少工具结果 | Q21 已确认等待当前执行完成或超时收尾、记录结果后暂停；具体完整消息位置及 SDK 接入仍待验证 |
| 多个原会话分叉位置来自不同时刻 | 各成员理解的主世界不同 | 是否建立共同任务版本；如何暴露各自快照时间差 |
| 全员初始暂停后，无建议者恢复工作，或用户修改相关状态 | 讨论依据可能与后续实际情况不同；全员初始暂停不等于持续冻结整个主世界 | 用户要求优先；不设自动失效检测或重议，后续由 Agent 发现问题并主动 @ 协调 |
| 任一主世界 Agent 迟迟未到可控边界，或讨论失败、超时 | 无法确认全员暂停或一直无法恢复 | Q21 不增加讨论启动退让重试；异常收尾、模型等待和进程故障统一处理，具体政策待定。讨论开始后的缺票沿用既有规则；不得默认强杀或自动放行 |
| 首轮无建议者被错误纳入第二轮 | 原 Agent 被重复暂停，或把不应投票的席位误判为缺票 | 已确认首轮无建议者退出第二轮；每轮必须使用对应参与名单 |
| 一场讨论进行中，已经恢复工作的无建议者又发起新讨论 | 全员重复暂停、多份上下文和投票、协调状态并发更新 | 允许并行，默认最多两场且可配置，超额排队；按讨论分别暂停，全部解除才恢复。分叉与提交顺序待细化 |
| D1 已结束但 D2 仍等待，错误地恢复同一原 Agent | Agent 提前运行，违反另一讨论的暂停要求 | 释放必须按讨论身份去重，不清空其他讨论暂停；恢复条件检查所有剩余暂停 |
| 应用全员参与，成员动态加入、退出或一个身份创建多个 fork | 投票人数变化、临时分身递归入选或重复计票 | 启动时固定首轮名单，之后新增者不加入；每身份每轮一票，临时分身不增席。名单内成员退出或无法分叉的处理待细化 |
| 最高票平票 | 无明确赢家，重复讨论可能无限延长暂停 | 仅首轮支持票者收到汇总及支持票理由并参加第二轮，省略无建议票逐条内容；仍平票交用户 |
| 全部席位均投无建议 | 没有任何候选方案获得支持 | 直接交用户、不自动重投；各原 Agent 按无建议规则解除本讨论暂停，不将释放或无建议视为同意 |
| 超时、进程崩溃导致缺票 | 少数票偶然决定全局，或无限等待 | 已确认限时等待，仍缺票则交用户；用户裁决被系统记录前补齐缺票可取消对应询问。等待参数与部分补票展示待细化 |
| 用户裁决与迟到投票同时到达 | 取消已提交决定、出现两个赢家或重复更新主世界 | 已确认以系统接收并记录用户裁决为分界，此后迟到票只留档；用户提交与取消互斥。存储、去重与恢复实现待设计 |
| Agent 有相关上下文但不支持任何固定候选方案 | 不能新增方案，也不应强行表达支持 | 已确认投无建议，不支持任何方案、不阻断其他方案胜出；原 Agent 后续读取消息变化后可自行 @ 协调 |
| 多数 Agent 共享相同错误假设 | 票多并不等于事实正确 | 证据要求、测试结果和用户约束如何约束方案 |
| super agent 更新决定、任务或 @ 状态后崩溃，通知未完成 | 主世界记录不一致、重复安排任务或漏通知 | 协调状态更新去重、提交边界及通知恢复；原 Agent 的执行结果另行核验 |
| Agent 被用户停止后又收到 @ | 自动恢复违背用户停止意图 | 停止状态是否阻止自动唤醒、由谁解除 |
| 相同争议重复发起，询问又触发询问 | 无限讨论、成本增长 | 合并、去重、轮数和预算上限 |
| 讨论完成后回写了全部对话 | 污染原 Agent 上下文，破坏无感知约束 | 仅结果通知的接收者、内容和审计访问范围 |

## 8. SDK 复用计划与证据

核验基线：2026-09-11，锁定/安装版本 `0.3.267`。以下为官方文档与本地类型的静态核验，不代表已经做过真实模型、分叉或消息送达测试。实现前仍需按 `agent.md` 重新核对。

| 需求 | 优先复用能力 | 已知边界或待验证项 |
| --- | --- | --- |
| Agent 执行与持续输入 | `query`、`AsyncIterable<SDKUserMessage>` | 当前应用尚未改为持续会话；不重写 SDK Agent 循环 |
| 主会话恢复 | 按明确会话 ID 使用 `resume` | transcript 恢复不包含应用 inbox、处理确认或外部操作回滚 |
| 讨论会话分叉 | `resume` + `forkSession: true`，按需指定 `resumeSessionAt` | 原生复制会话历史到新会话；不快照文件系统；运行中来源的原子分叉保证尚未核实 |
| 上下文追加 | `SDKUserMessage.shouldQuery` | 输入追加和实际触发推理不同；送入上下文不等于已处理 |
| 显式中断 | 流式 query 的 `interrupt()`，结合应用生命周期控制 | 不回滚已发生操作；不默认清除已经排队的输入 |
| inbox、讨论、投票能力 | 内置 Bash → raftctl 本地 CLI；Skill 提供用法 | 最新约束不采用 MCP；应用服务负责业务语义和权限检查 |
| 可控边界提示 | Hooks，如 `PreToolUse`、`PostToolUse` | 提示不等于确定性暂停或禁止操作；具体 hook 语义须逐项核验 |
| 同机会话通信 | 官方 `ListAgents` / `SendMessage` 能力 | 文档描述工具调用间接收、空闲会话开启新一轮；SDK 打包 CLI、工具暴露、配置与服务适配仍需运行验证；不等于恢复已退出进程 |
| 命名子代理 | SDK `agents` / Agent 工具及文档中的消息扩展 | 普通子代理与继承指定原会话的 fork 不应混同 |
| Agent Teams | 仅参考概念 | 官方文档说明 headless / Agent SDK 会话不能创建 teammates，不能照搬交互式 Teams |

### 会话分叉专项核验

- 安装类型与官方会话文档支持 `query` 的 `resume`、`forkSession: true`、`resumeSessionAt` 组合。`resumeSessionAt` 指定包含在分支中的截断消息；分支得到独立会话 ID，后续对话不写回来源会话。
- 安装版本还导出独立的 `forkSession(sessionId, { upToMessageId?, title?, dir? })` 辅助方法。本次仅核实其本地类型，未核实相应公开参考正文；不作为首选实现前提，也不要与 Options 中的同名布尔选项混淆。
- SDK 分叉不包含文件系统快照、进程调用栈、正在执行的操作或尚未形成可恢复消息的内部状态。
- 当前文档与类型未给出本次可以依赖的“运行中来源原子快照”保证。候选策略是记录 `sourceSessionId + branchPointMessageId`，从应用确认的完整消息边界分叉；这是待验证的一致性策略，不能宣称 SDK 已自动保证。
- 不应机械选择最后一条 assistant 消息作为完整执行边界，后续可能还有工具结果或结构化结果。
- 会话持久化默认开启；关闭持久化会影响调用结束后的恢复。应用必须保存自身 Agent 身份与 SDK session ID 的映射。
- fork 启动时应显式派生配置，包括角色提示、模型、本地内置工具、CLI 能力范围、Skill、hooks、权限、工作目录和预算。官方恢复文档明确部分启动参数需要重新提供；“有历史上下文”不等于“原配置全部自动继承”。自定义 system prompt 在不同恢复方式下的精确行为仍需验证。

### 工具与房间隔离专项核验

- `allowedTools` 表示自动批准，不是工具白名单。`tools` 控制基础内置工具集合，不能据此断言 MCP 已禁用。
- 显式配置内置工具、审核 CLI 命令权限与 hooks，并使用适用的拒绝规则及文件访问隔离。MCP server 配置为空并禁用额外发现，启动时检查实际工具列表。`canUseTool` 不是每次工具调用必经的拦截点；如需每次调用检查，应核验 `PreToolUse` 等机制及其拒绝语义。
- 原生同机消息发现与发送不会自动理解应用的讨论 `roomId`。若最终选择只允许经房间工具通信，候选配置需要同时处理接收与发送：`settings.crossSessionInbound: 'refuse'` 拒绝原生 peer 消息，禁止 `SendMessage` / `ListAgents` 阻止原生发送与发现。只禁止发送不能阻止接收。
- 上述设置在安装类型与官方文档中有依据，但与自定义房间通信的组合仍需运行验证。自定义工具服务应从宿主绑定的身份判断席位和房间权限，不能信任模型自行声称的 Agent ID。
- 如果确需自定义房间通信，理由应限定为成员授权、讨论隔离、业务持久化等原生通道尚未满足的要求，而不是假定 SDK 没有消息能力。

## 10. 后续实现与验收对齐

开始实现某一部分前，需要先冻结其依赖的产品决策，记录适用 SDK 能力与自定义部分的理由。其余未决问题可以保持开放，但不能在代码中静默选定。

后续验收应覆盖：

1. 具体代码任务完成分工、实现、审查与冲突纠正，留存消息对行动产生影响的证据。
2. B 因 @ 发起讨论；fork 继承指定位置的上下文，新增讨论未污染原会话。
3. fork 无法修改主世界，投票仅能写对应房间的合法席位和方案。
4. 最终结果主动通知主要参与方，不向非主要参与方自动注入讨论过程或结果；其他原 Agent 可在后续主动读取 inbox 变化时获知结果并协调。
5. 平票、无建议、缺票和重复应用按最终确认的规则处理；不要求实现语义上的裁决失效自动判断。
6. 重启后能关联消息、读取进度、原会话、讨论和裁决应用记录；不因消息重放盲目重复操作。
7. 用户显式停止与普通 @ 的行为不同；测试不把中断描述为副作用回滚。
8. 开始讨论时全部主世界 Agent 在可控执行边界暂停；分身投无建议后对应原 Agent 解除本讨论暂停，投支持票或未投票者继续等待最终结果。主要参与方身份不再决定是否初始暂停，暂停不等于整个主世界冻结。
9. 讨论成员范围覆盖整个应用的主世界 Agent，不因任务归属不同而过滤成员；每个主世界身份一票，临时分身不增加席位，同一身份的多个分身不得重复计票。成员变更按后续确认的规则处理。
10. 第一轮平票后，只有首轮支持票者参加一次补充讨论与重投；仍平票交用户，不自动开启第三轮。第二轮参与 fork 接收汇总和支持票理由，省略无建议票逐条内容；无建议者不参加、不接收补充上下文，原始票记录不删除。
11. 全部席位均投无建议时直接交用户处理，不自动重投、不产生默认赢家；各原 Agent 按无建议规则解除本讨论暂停，不代表争议请求获批准。未响应或失败不能被当成无建议。
12. 缺票限时等待后交用户，保留已有投票；系统记录用户裁决前，缺票补齐可取消询问并恢复计票。用户裁决已被系统记录后迟到票只留档，不覆盖决定；并发用户提交与取消只有一个成功。补票后仍需进入正常计票及异常分支。
13. 本轮席位均提交有效票后，支持票唯一最多的方案胜出，不要求过半；例如 X 三票、Y 两票、Z 两票、无建议三票，应判 X 胜出。
14. super agent 只承担已确认的协调职责：更新决定、任务安排、触发讨论的 @ 状态并通知主要参与方；实际代码修改与任务命令由原 Agent 执行。@ 状态、通知和任务完成按各自语义验证。
15. 决定与任务安排登记后，@ 由讨论中变为已裁决并关联后续任务；代码执行尚未完成也不继续将旧 @ 作为待裁决消息。读取进度和执行结果不因该状态转换被自动标为完成。
16. super agent 不能因自身偏好改变赢家，也不增加裁决失效自动检测、暂停应用及自动重议流程。
17. 用户要求优先于 Agent 投票及 super agent 的判断；用户明确改变要求后，不能继续应用与其冲突的旧裁决，也不能要求 Agent 投票通过后才承认该要求。
18. 后续问题由 Agent 主动 @ 相关 Agent，接收方发现冲突时按普通讨论入口处理；不通过隐藏的失效检测器自动创建新讨论。
19. 首轮无建议者不参加第二轮，其原 Agent 继续工作，不因第二轮重新暂停；第二轮不将其视为缺票。非主要参与方投支持票时同样等待最终结果；宿主放行不得向其原会话注入未经授权的讨论上下文。
20. 第一轮各分身独立提交选择与理由，不能查看其他分身本轮投票意见；平票后仅第二轮参与者收到首轮汇总及支持票理由。独立答询不能绕过这一隔离规则。
21. 发起时固定候选方案，两轮共用同一集合及方案内容；投票工具不得接受分身临时创建的选项或同一 ID 下被修改的方案。方案引用与输入校验按后续接口设计验证。
22. 有相关上下文但均不支持时可投无建议，沿用其计票、提前恢复及首轮退出第二轮规则，不新增否决票；原 Agent 后续读取消息变化后仍可主动提出新问题并按普通 @ 流程协调。
23. 第二轮各参与分身读取首轮汇总与支持票理由后独立重判；不互相交换本轮实时意见，不增加自由辩论阶段。首轮无建议者不因此重新加入。
24. 同一身份同轮只能接受一张有效票；同内容重试不重复计数或重复释放，不同内容不覆盖。合法第二轮参与者须重新投票，计票不累加或借用首轮旧票。
25. 支持票对应原 Agent 只有在协调状态与主要参与方结果通知均写入后才解除本讨论暂停；计票完成但写入未完成时不放行。通知写入不自动推进已读，不解除其他独立停止条件。
26. 多场讨论可以并行；某原 Agent 受 D1、D2 暂停时，D1 无建议或结束只解除 D1，不能越过 D2 恢复执行。每场票、分身及通知隔离，不因同一来源身份而跨房间混用。
27. 默认最多同时启动两场讨论，上限可配置；超额请求排队，未实际启动的请求不创建整组分身或施加全员暂停。等待用户的讨论继续占名额，两场均等待时不能启动第三场；迟到结果处理不重复占用名额。
28. 首轮名单在实际启动时固定：排队期间加入且启动时仍属主世界的成员参与，启动后新增者不加入；临时分身不计入名单，第二轮从本场首轮支持者派生。
29. A、B 已暂停且位置已记录，C 尚未到达可控边界时，不得创建 A′、B′ 或接受其投票；只有名单内全员完成暂停及可恢复位置记录后才创建本场讨论 fork。暂停请求已发出不能冒充暂停确认，也不能把本规则解释为文件快照保证。
30. 暂停请求到达后，当前工具正常返回或超时收尾均可进入暂停确认路径；先保留完整结果，不让原 Agent 继续下一步或自动重试。只有调用方超时、底层操作未收尾时不能伪造暂停成功；第一版不实现讨论启动专用退让重试。通用运行时故障的最终处理按后续政策验证。
31. 本场文件快照建立后，C′ 投无建议、原 C 恢复并修改代码；尚未完成投票的 A′、B′ 及后续第二轮仍读取本场快照版本。不得自动刷新快照、转读主世界最新文件，或因主世界变化自动重开讨论。该检查不声称原会话历史与文件快照完全同步。
32. 在确定纳入快照的文件范围内，修改已跟踪文件但不提交、新建未跟踪文件、删除已有文件后创建快照；分身应看到暂停后的实际内容及缺失状态，不得退回最近一次提交，不得要求先提交 Git。具体纳入范围及排除规则另行验证。
33. 发起者未引用的项目源码、测试、文档和必要配置，只要符合项目快照规则，仍可供分身按需读取；依赖、缓存、Git 内部数据、应用运行状态及凭证文件按统一规则排除。不能把“纳入快照”实现成自动注入全部文件正文；确切路径匹配按后续细则验证。
34. 原 C 因无建议恢复并获得新上下文后，A′ 才发起对 C 的答询；答询分身仍使用本场暂停时固定的 C 原会话位置和本场文件快照，不读取 C 后续会话，也不继承 C′ 的投票意见。答询不回写原 C，不新增投票席位。
35. A′ 连续向 C 追问时，其专属 C 答询会话保留此前问答；B′ 向 C 发问时使用独立会话，不能读取或被注入 A′ 的问答。同一提问者在不同讨论房间也不能混用答询上下文；不得因复用而增加目标身份的投票席位。
36. A′ 询问 C 的答询分身，后者发现缺少 D 的信息时，只向 A′ 返回缺口，不直接向 D 发消息、调用答询工具或创建新分身。A′ 可按其权限另行询问 D；原 C、D 本体均不因该答询收到新输入。
37. A′ 合法进入第二轮后继续向 C 答询时，可沿用自己首轮的专属会话及此前问答；不得读取 B′ 对 C 的问答，不刷新原 C 来源或文件版本，不向其提供其他分身第二轮实时意见。首轮无建议者不能因保留答询会话而重新投票。
38. A′ 的一次答询超时或失败后，应收到明确失败结果，并可在既有权限及期限内继续判断、查询或显式投票；宿主不能自动写入无建议、释放其暂停或直接请求用户裁决。A′ 最终未提交有效票时，仍按本轮缺票规则处理。
39. 同一席位本轮跨目标累计执行 5 次答询后，第 6 次新答询应被额度限制拒绝；失败请求计入，已有请求的幂等重传不重复扣减。第二轮合法席位单独计次，复用答询会话不携带首轮已用额度。额度耗尽不能自动生成投票、释放暂停、询问用户或延长投票期限。
40. 讨论启动但 A′ 尚未向 C 询问时，不预建 A′ 专属的 C 答询分身；首次合法询问才创建，后续追问复用。即使原 C 已继续工作，创建仍绑定本场固定来源和文件快照，不刷新为最新状态；投票讨论分身仍覆盖本场全员席位。
41. `view_inbox` 查询或返回消息后尚未收到接收 Agent 的显式已读确认时，消息继续未读；确认指定消息 ID 后，只更新对应接收者的已读记录，不自动标记处理完成、裁决完成或任务完成。未确认消息重现不代表可重复执行其请求；重试执行仍需独立去重与核验。
42. 当前 Agent 同时有两条未读 @ 与五条普通未读时显示“@ 消息”；只确认两条 @ 已读后显示“新增消息”，五条普通消息仍未读；全部已读后即使关联任务未完成也显示“未新增”，任务待办继续独立存在。
43. 正常运行中的 Agent 在工具执行期间收到新消息，提醒应等可控边界再提供；提醒包含状态与未读数量、有未读 @ 时引导优先查看，不直接注入消息全文，不自动标读。正文通过 `view_inbox` 拉取，Agent 自行判断行动调整；该测试不代替暂停或已退出 Agent 的独立唤醒政策。
44. 同一工具执行期间连续收到五条新消息，在下一可控边界合并提醒；成功提醒后无新增，即使这些消息仍未读，也不在后续边界重复注入。随后再收到新消息应重新触发提醒，包括未读总数因同时确认旧消息而保持不变的情况；原未读记录不得因合并或提醒成功被清除。
45. 仍登记在应用的 Agent 自然空闲或正常结束运行后，普通新消息和 @ 均可触发恢复原会话并检查 inbox；唤醒不得自动重放旧任务或直接执行消息要求。存在用户停止、讨论暂停等阻塞时，保存消息但不得由消息解除阻塞或启动工作；异常退出与会话不可恢复按后续故障政策验证。
46. 空闲的 A 同时收到多条消息时，仅启动一个 A 的主世界实例；启动中或运行中新增消息继续保留，由该实例检查或按边界提醒。不得因消息另起重复实例或绕过暂停；讨论与答询 fork 仍可按各自规则运行。退出交界与恢复时的消息不丢失、实例归属另行验证。
47. A 同时受两场讨论暂停期间收到三条新消息，消息入库但不唤醒或注入；只结束第一场时不补送，第二场也结束且无用户停止等其他阻塞后才合并补送。补送不自动标读，不重复催读暂停前已提醒的旧消息，不改变既有裁决结果通知范围。
